# Expansions — EXP-01 … EXP-14

Drafted 2026-07-01. Three horizons: **H1** deepen the core, **H2** adjacent
capabilities/audiences/integrations, **H3** transformative bets. Net-new
relative to `docs/ROADMAP.md` (P-items), the R-backlog, and the branch
RR/RE-items; overlaps are cited and exceeded, not repeated. Effort tiers as
in `02-large-scale-fixes.md`.

---

## H1 — Deepen the core

### EXP-01 — Structured fare-fact layer

**Pitch:** extract every price, age bound, proof document, and
application-location fact into a typed, per-agency fact table at ingest, and
verify numeric claims in answers against it deterministically.

**Impact:** converts a chunk of "groundedness" from LLM-judge opinion into
arithmetic. The two chronic failure classes — a price attributed to the
wrong program (conv-005/ml-004 contact over-attribution) and a dropped
asked-for figure (ground-026) — become checkable without a judge: an answer
that states "$20" either matches a fact row scoped to that program or it
does not. Also the substrate for EXP-04, EXP-07, and the EXP-06
cross-validation.

**Shape:** a `FareFact` dataclass (agency, program, rider_class, price,
currency, age_min/max, proof_docs, apply_where, apply_cost, source chunk_id)
extracted in `src/assistant/ingest.py` from the already-normalized tables
(ADR 0005 did the hard part: transposed-table normalization); committed as
`corpus/processed/facts.jsonl` with the corpus version; a new deterministic
check in `evals/checks.py` that parses `$`-amounts and ages from answers and
requires each to match a fact row consistent with the cited doc. Extraction
imperfection is fine if honest: facts carry a `confidence: parsed|manual`
flag and unparsed tables fall back to today's behavior.

**Effort:** L. **Risks:** extraction errors become false eval failures —
start manual-verified for the five agencies (12 documents is small), then
automate. **Excellence bar:** ≥90% of price/age claims in answered cases
verified deterministically; conv-005-class misattribution caught by a
deterministic check, not only the judge.

### EXP-02 — Counterfactual sensitivity suite

**Pitch:** minimal-pair eval cases that assert answers *change when they
should and hold when they should not* (62 vs 65, Medicare vs Medi-Cal,
MST vs SBMTD, monthly vs single-ride).

**Impact:** today every case grades one question in isolation; nothing
checks that the system distinguishes near-neighbors — exactly where riders
get hurt (the research panel's F-15 "two ways to qualify" confusion is a
symptom). Sensitivity testing is a different axis from RE4's adversarial
baiting: no adversary, just the boundary.

**Shape:** a `sensitivity.yaml` suite where each case is a *pair* (or
triple) of questions with per-variant `required_facts` /
`forbidden_content`; runner support for pair-cases is small (they are
independent single-turn calls scored jointly); author ~15 pairs from the
published boundaries already catalogued in `evals/suites/edge_cases.yaml`
rationales. The deterministic half validates offline; judge half is
live-gated.

**Effort:** M. **Risks:** doubles model calls per pair (FIX-12 mitigates).
**Excellence bar:** a published sensitivity score ("N/15 boundary pairs
correctly distinguished") in `EVALS.md`, stable across two consecutive live
runs.

### EXP-03 — Eval-history trend artifact

**Pitch:** render the 31 committed run directories under `evals/runs/` into
a single trajectory page — per-suite pass rates, cost, and duration over
time, annotated with prompt/corpus version changes.

**Impact:** `CLAUDE.md` says "the improvement curve across commits is part
of the story" and `docs/audits/methodology.md` cites "the 51→96 improvement
curve in the git history" — but the curve exists only for readers willing to
parse JSON in 31 directories. For the procurement/journalist audience this
is the cheapest possible credibility artifact, and it makes score *decay*
(post-merge staleness, FIX-01's concern) visible too.

**Shape:** `evals/history.py` walks `evals/runs/*/summary.json`, emits
`docs/eval-history.md` plus a small static SVG/HTML chart (same
no-dependency discipline as `web/offline.py`); regenerated by `make report`;
distinguish offline/mock runs from live runs honestly (they are different
instruments).

**Effort:** S–M. **Risks:** none real; guard against implying comparability
across mode changes (smoke vs full vs offline). **Excellence bar:** one
linkable page where the 2026-06-12 → present trajectory, each prompt bump,
and each cost figure is visible; README links it.

### EXP-04 — Structured answer contract

**Pitch:** answers become a typed payload — criterion, price(s), proof
documents, next step, decision-owner, as-of, citations — rendered by the UI,
instead of a single prose blob that prompts try to shape.

**Impact:** the last three prompt bumps (v6 asked-for-price, v7 positive
handoff/RR4, v4 close-the-loop/RR1) are all attempts to force structure
through prose instructions, each validated only by judge. A schema makes the
contract checkable field-by-field (`next_step` present? `decision_owner`
named? price list non-empty when a fact row matches?), makes staff mode
(RE3) a rendering choice instead of a second prompt, and gives screen-reader
users semantic regions instead of a text wall (persona F-9).

**Shape:** answer model emits JSON conforming to a committed schema
(`docs/answer-contract.schema.json`); `answer.py` validates, falls back to
prose on parse failure (counted, never hidden); `evals/checks.py` gains
per-field checks; `web/index.html` renders sections with proper headings.
This is a major prompt+pipeline change: it must ride FIX-01 provenance,
FIX-12 cheap runs, and a full live regression cycle.

**Effort:** XL. **Risks:** structured output can degrade answer naturalness
in Spanish; parity table must be watched; the citation-per-claim discipline
must map into fields. **Excellence bar:** every RR1/RR4-style requirement is
a deterministic field check; prose-fallback rate <5%; a11y walkthrough
(RR7) confirms the sectioned rendering reads better, not worse.

### EXP-05 — Longitudinal, time-versioned corpus

**Pitch:** stop overwriting snapshots; keep every corpus version, indexed by
`corpus_version` and date, and make "what changed when" a first-class query.

**Impact:** today `make fetch` replaces `corpus/raw/` in place and history
lives only in git. A time-versioned store turns the freshness story from
"we are dated" into "we are a record": agencies get an audit trail for what
the assistant would have said on date X (a liability-candor asset, given the
Air-Canada-style precedent in RESEARCH-ROADMAP E1), RE7's rider-readable
changelog gets real data depth, and researchers get a small longitudinal
fare-policy dataset — a genuinely scarce public artifact.

**Shape:** `corpus/versions/<corpus_version>/` retaining processed chunks +
manifest snapshot (raw HTML optional, size-permitting); `assistant/corpus.py`
grows `load_chunks(version=...)`; `diff_corpus` chains across versions to
build the full changelog; `/version` optionally lists known versions. The
serving path stays pinned to one version — no time-travel answering for
riders (that would be a freshness-confusion hazard), just provenance.

**Effort:** L. **Risks:** repo size (mitigate: processed-only retention);
must not weaken the "answers reflect the current snapshot" simplicity.
**Excellence bar:** for any past live eval run, the exact corpus it saw is
loadable by version id; the changelog is generated, not hand-seeded.

## H2 — Adjacent capabilities, audiences, integrations

### EXP-06 — GTFS-Fares cross-validation channel

**Pitch:** ingest the agencies' machine-readable GTFS(-Fares) feeds as a
second, structured evidence source and continuously cross-check them against
the prose corpus — disagreement becomes a freshness/accuracy alarm.

**Impact:** California (Cal-ITP) actively standardizes GTFS publication, and
the corpus already overlaps the two Cal-ITP Benefits agencies (MST, SBMTD).
Prose pages and feeds drift at different speeds; a detected disagreement
("web page says $2.50, feed says $3.00") is precisely the wrong-fare
liability scenario buyers fear (RR2's rationale), caught mechanically. Also
grounds EXP-01 facts in a second source.

**Shape:** a `gtfs` fetch path in `ingest.py` (feeds are zipped CSVs;
parsing fare_attributes / the Fares-v2 files is dependency-light);
cross-check job comparing feed fares to EXP-01 fact rows per agency;
disagreements land in the FIX-09 freshness PR body and, when confirmed, as a
dated caveat line in affected answers. Honest caveat: which of the five
agencies publish usable Fares data was *not* verified in this pass — step
one is a survey, and the design must tolerate "feed absent."

**Effort:** L. **Risks:** feed quality varies; never auto-prefer feed over
prose (agencies' published prose is the citable policy; the feed is a
tripwire). **Dependencies:** EXP-01. **Excellence bar:** every fact row
carries a `feed_agrees: yes|no|no_feed` flag; at least one real drift caught
and PR'd before claiming the feature works.

### EXP-07 — No-model guided fare finder

**Pitch:** a deterministic "which fare applies to me" walk-through (agency →
rider category → the published criteria, prices, proofs, next step) built
entirely from the EXP-01 fact table — zero model calls, works on `/offline`.

**Impact:** serves the riders the chat modality serves worst — no signal
(P6/F-11), low literacy, screen-reader users who prefer forms to chat — at
zero marginal cost and zero hallucination risk, because it renders published
facts verbatim with citations. It is also the strongest possible
demonstration of the no-determination line: a UI that shows criteria and
*never computes* eligibility even though a form-like UI invites it (the
design must resist adding "enter your age").

**Shape:** static generation in the spirit of `web/offline.py`: pre-render
the decision tree per agency from facts.jsonl into accessible HTML
(details/summary or plain anchor navigation, no JS required), served at
`/guide`; same a11y gate as other pages; eval-side, a parity check that
every fact row is reachable in the rendered guide.

**Effort:** M (given EXP-01). **Risks:** the form-factor temptation to
collect rider attributes — the excellence bar below forbids it.
**Excellence bar:** zero input fields; passes `web/a11y.py`; usable printed;
every screen carries source + as-of; riders reach a next-step line in ≤3
taps.

### EXP-08 — SMS access channel (design-gated)

**Pitch:** the same guarded pipeline over SMS for riders without smartphones
or data plans.

**Impact:** the offline page helps riders who planned ahead; SMS reaches the
rider standing at the stop with a feature phone. Equity reach beyond
anything the web demo can do.

**Shape (and why it is gated):** an SMS gateway (e.g., a Twilio webhook in
front of the existing `answer_question`) necessarily *receives phone
numbers* — which the hard rules classify as PII the system must not persist.
A compliant design (immediate number hashing for the reply routing, no
logging, provider data-retention settings, short-code costs) needs a real
privacy review before any build, and provider contracts cost money. Do the
one-page DPIA-style design first; build nothing until it survives review.

**Effort:** L (after gate). **Risks:** PII-by-transport contradiction with
the no-PII posture if designed casually; per-message costs. **Excellence
bar:** a committed privacy design that a skeptical reviewer signs, then a
pilot in one agency's service area with content-free operational logs only.

### EXP-09 — Agency operator console

**Pitch:** a small authenticated surface where an agency owner approves a
corpus version (the `FPA_PINNED_CORPUS_VERSION` flow), reviews the
changelog/diff, configures embed ancestors and theming, and reads the latest
eval report — the operational half of the pin feature that exists only as
env vars today.

**Impact:** R2-6/RR-era work built the mechanism (pin, `/version`,
`diff_corpus`); the *operator experience* is still "edit a Lambda env var,"
which no comms manager (P12) will ever do. This is the difference between
"an agency could run this" and "an agency's non-engineer can operate this."

**Shape:** static-plus-API like the rest of `web/`; authentication is the
real design question (the demo is deliberately accountless — the console
must be a separately deployed, separately authenticated surface, e.g. behind
the agency's own SSO/IAM, never on the rider Lambda); actions are limited to
config reads/writes, no rider data exists to expose.

**Effort:** L–XL. **Risks:** scope creep into a SaaS admin panel, which the
ROADMAP's out-of-scope list forbids — keep it single-tenant,
deploy-it-yourself. **Excellence bar:** an operator can pin, review a diff,
and update embed origins without touching AWS consoles, documented in
`infra/README.md`.

### EXP-10 — "Add an agency" contribution kit

**Pitch:** a scaffold that turns adding a sixth agency into a guided PR:
manifest entry template, fetch/ingest run, auto-drafted eval-case skeletons
from the new chunks, and a parity checklist.

**Impact:** ROADMAP P3-1 treats new agencies as bespoke work by the author.
The corpus's growth path — and the credibility of "same eval coverage as the
existing four" — depends on making the *case-authoring* discipline
transferable. This is also the on-ramp for outside contributors that
`CONTRIBUTING.md` currently lacks a meaty task for.

**Shape:** `python -m assistant.scaffold_agency <id>` generating manifest
stanza, per-chunk case-skeleton YAML (id, question stub, the source passage
inline as the rationale, empty required_facts to be filled by a human),
and a checklist (robots notes, ES page?, parity mirror plan, edge-case
boundaries found); documentation in `docs/adapting.md`'s style.

**Effort:** M. **Risks:** auto-drafted cases must never be committable
without human-filled facts — enforce with a `draft: true` flag the runner
refuses. **Excellence bar:** a contributor who has never seen the repo lands
agency #6 with full suite coverage in one reviewed PR.

### EXP-11 — Second-domain live proof

**Pitch:** actually stand up the promised sibling — a benefits-adjacent
policy explainer (e.g., housing-voucher or CalFresh *policy explanation*,
never eligibility) built from a `DomainProfile` fork, deployed, and
evaluated with the same harness, publishing the comparative report.

**Impact:** `docs/adapting.md` and R3-3/P3-5 argue the harness generalizes;
a test profile in the suite is evidence, a second live domain is proof. For
the portfolio thesis ("here is how to test civic AI"), one working
generalization is worth more than three more transit agencies. It also
stress-tests FIX-06 (late binding) and the guards' domain seams for real.

**Shape:** ideally in the civic-rag-starter-kit repo (this repo's stated
generalization target), consuming this repo's pattern; the deliverable
*here* is the comparative writeup: what transferred, what leaked, hours
spent, eval scores side by side.

**Effort:** XL (cross-repo). **Risks:** domain gravity — benefits domains
are higher-stakes than fares; the will-not-do list must be rebuilt with the
same care (adapting.md step 2), and counsel-adjacent framing questions
(what counts as benefits advice) need an SME read. **Excellence bar:** a
published "we forked it in N days, here is the honest delta" document with
both scoreboards.

## H3 — Transformative bets

### EXP-12 — Statewide fare-policy commons

**Pitch:** scale the corpus discipline (dated snapshots, provenance,
versioning, per-agency eval coverage) toward all California transit
agencies, publishing the result as a maintained open dataset + API others
build on.

**Impact:** ~200 CA agencies publish fare policy as scattered prose; nobody
maintains a dated, versioned, machine-usable record. The commons — not the
chatbot — may be the durable public good: 511-style services, researchers,
Cal-ITP, and other assistants could all consume it. This repo already owns
every ingredient (manifest discipline, corpus_version, diff, freshness
automation, EXP-01 facts, EXP-05 history).

**Shape:** phase it: (1) 10–15 agencies with the EXP-10 kit and FIX-07's
corpus-growth-safe decline rule; (2) extraction QA tooling and per-agency
maintainer docs; (3) a static dataset site (facts.jsonl + chunks per
version, CC-attribution posture consistent with the manifest's license
notes). The assistant becomes one consumer among several.

**Effort:** XL, sustained. **Risks:** maintenance burden is the whole risk —
without automation (FIX-09) and contributors (EXP-10) this decays into 200
stale snapshots, which is worse than 5 fresh ones; robots/permission notes
must be per-agency verified as `corpus/manifest.yaml` models. **Excellence
bar:** a published dataset with monthly freshness SLO, per-document
provenance, and at least one external consumer that is not this repo.

### EXP-13 — Local-model kiosk variant

**Pitch:** run the identical guarded pipeline on a small local model (or in
retrieval-only mode) for offline kiosk deployment at transit centers, and
publish the eval delta between local and Bedrock backends.

**Impact:** transit lobbies and libraries have exactly the riders the demo
misses; a kiosk with no network dependency and no per-query cost changes
the deployment economics for small agencies. Equally valuable: the
`models.py` Protocol adapter plus the 118-case harness makes this the rare
place where "how much worse is a small local model, exactly?" gets a real,
published answer — including where the guards catch the extra failures.

**Shape:** a fourth backend in `src/assistant/models.py` (llama.cpp/Ollama
style, offline); run the full suite per backend, publish the comparative
scoreboard as an ADR-grade document; if local generation fails the bar,
the honest fallback is EXP-07's no-model guide on the kiosk instead —
"we measured, generation didn't clear it" is a perfectly good published
result.

**Effort:** L for the experiment, XL for a hardened kiosk build. **Risks:**
local models fail the citation/no-determination discipline more often —
which the guards are built for, but rider experience degrades into
refusals; hardware/venue partnerships are a real-world dependency.
**Excellence bar:** a committed backend-comparison report with per-suite
deltas and guard-trip rates; a go/no-go criterion stated *before* running.

### EXP-14 — Conformance program: the harness as a certification instrument

**Pitch:** grow RE5's "stamped audit profile" into a versioned public
conformance definition — "Fare-Assistant Conformance Profile v1: these
suites, these thresholds, this judge protocol" — that any transit chatbot
operator can run against their own system and cite, with a public registry
of self-reported results.

**Impact:** the market context (RESEARCH-ROADMAP E11: CTA, MTA, WMATA
deploying bots with no public accuracy claims) means the eval definition may
matter more than any single assistant. A named, versioned bar ("passes
FACP-v1") is the thing a procurement officer can put in an RFP — the E13
NIST-crosswalk logic taken to its conclusion. This is the portfolio's
GovChat-Eval flywheel: this repo defines the domain profile, GovChat-Eval
executes it.

**Shape:** extract the suite definitions, thresholds, and judge protocol
into a versioned spec document + a GovChat-Eval profile; a
`conformance/` runner mode that any HTTP-fronted fare bot can be pointed at
(RE5's adapter is the execution half; the *spec and registry* are the
net-new half); registry entries are self-reported with published evidence
bundles, never third-party scans of others' systems without consent.

**Effort:** XL. **Risks & gates:** naming thresholds that others must meet
is a normative act — it needs SME review (a transit accessibility officer, a
Title VI officer, an eval researcher) and probably counsel comfort on
certification-like language ("conforms" vs "certified"); premature
authority would violate the honesty ethos. Sequence strictly after RR6
(calibrated judge) and FIX-04 (variance), because a certification bar built
on an uncalibrated instrument is exactly the dishonesty this portfolio
exists to reject. **Excellence bar:** FACP-v1 published with rationale per
threshold, at least one *external* system evaluated by its own operator
against it, and a documented revision process.
