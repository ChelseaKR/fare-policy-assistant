# Internationalization & localization status: gettext (EN/ES/TL)

The fare-policy-assistant renders its **fixed, rider-facing strings** in
**English, Spanish, and Tagalog** through GNU **gettext** message catalogs, per
[`INTERNATIONALIZATION-STANDARD.md`](https://github.com/ChelseaKR/portfolio-standards/blob/main/INTERNATIONALIZATION-STANDARD.md) §3/§4. This replaces
the previous bespoke EN/ES Python dict (`guards._REFUSAL_MESSAGES`) and the
`if lang == "es"` branch in `answer._no_support_message`, which had no extraction
tooling, no key-parity check, and no placeholder-parity guard.

Declared: 2026-06-30 · Reviewer: fare-policy-assistant maintainers

---

## What is (and is not) translated

**Translated — the fixed rider-facing strings.** These are the strings the code
emits verbatim (not model output), and there are six of them:

- the three input-guard refusals — PII, out-of-scope, and prompt-injection
  ([`guards.check_input`](../src/assistant/guards.py) → the message text now in
  [`i18n.refusal_message`](../src/assistant/i18n.py)); and
- the "no published policy answers that" decline, in its agency-specific and
  statewide-pointer forms ([`answer._no_support_message`](../src/assistant/answer.py)
  → [`i18n.no_support_message`](../src/assistant/i18n.py)).

The rider's language is chosen from the *content* of the question
([`guards.detect_language`](../src/assistant/guards.py)); the same signal already
powers the eval language-match check.

**Not translated — by design.** The standard scopes i18n to end-user text, so
these carry **no** `_()` calls:

- **the model's answer text and the prompts** under [`prompts/`](../prompts) — the
  answered response is written by the model from retrieved passages, not fixed
  text this catalog owns (out of scope for this migration; the model is asked to
  answer in the rider's language);
- **the retrieval query-expansion synonyms** in
  [`retrieve.py`](../src/assistant/retrieve.py) — those are retrieval logic, not a
  displayed string;
- **the guard *detection* patterns** in [`guards.py`](../src/assistant/guards.py)
  (PII, injection, determination-language, citation, and as-of regexes) and
  [`domain.py`](../src/assistant/domain.py) (scope-topic regexes) — these are
  control flow. Migrating strings must not weaken them, so **only the displayed
  message text moved**; every detector is unchanged and the safety-guard tests
  still pass;
- **the CLI** ([`cli.py`](../src/assistant/cli.py)) and the **web handler's
  HTTP/JSON error bodies** ([`web/handler.py`](../web/handler.py)), which are
  English-only operator surfaces.

## The seam (how it works)

- [`src/assistant/i18n.py`](../src/assistant/i18n.py) — `get_translation(lang)`
  loads `messages.mo` for the language with `fallback=True` (unknown tags return
  the English source text, never an error). `refusal_message()` and
  `no_support_message()` are the label helpers that hold the six English source
  strings wrapped in `_()`. `negotiate_lang()` implements the §6
  `Accept-Language` fallback chain (`<requested> → <primary subtag> → en`) for a
  future negotiated HTTP surface — see Phase 3 below.
- The **source string is the English text itself** — e.g.
  `_("the agency's website or customer service")` — so extraction needs no key
  map. Placeholders use `.format()` (`{where}`, `{statewide}`).
- Catalogs live **inside the package** at
  `src/assistant/locales/{messages.pot, <lang>/LC_MESSAGES/messages.{po,mo}}`, so
  a checkout or an installed wheel resolves them with no separate install step.
- [`babel.cfg`](../babel.cfg) tells `pybabel extract` to scan the package sources.

## Spanish and Tagalog fixed-string status — complete

Spanish is **fully translated** and is **real, pre-existing human** translation:
it is carried over **verbatim** from the retired bespoke `_REFUSAL_MESSAGES` dict
and the `if lang == "es"` branch of `_no_support_message`. **No machine
translation was introduced**, and the rendered output is byte-for-byte identical
to what those dicts produced (verified by the guard/answer tests, which assert the
Spanish substrings).

Because real Spanish exists, the **G5 completeness gate is enforced as a hard
merge-blocker** (every msgid has a non-empty `msgstr` in both locales), *not*
downgraded to a structural-only check with an untranslated-ES follow-on. There is
no [REVIEW-GATE R3](https://github.com/ChelseaKR/portfolio-standards/blob/main/INTERNATIONALIZATION-STANDARD.md) translation backlog for the
current string set. Any *new* rider-facing string is added in English first and
must have its Spanish and Tagalog `msgstr` filled before merge (the gates below
block otherwise). Tagalog remains a stretch language for model answers because
the policy corpus has no agency-authored Tagalog page; the catalog covers the
deterministic guard and no-support strings, not the retrieved policy content.
Its translations are complete and mechanically gated but have not yet received
a fluent human-language review, so they do not promote Tagalog to a supported
production language.

## Live merge-blocking gates (`make i18n`, wired into `make verify` and CI)

Local `make i18n` and the CI `i18n` job run the identical target (no drift):

| Gate | What it checks | Mechanism |
|---|---|---|
| **G2-lite** | The extraction template is committed & current | `pybabel extract` → normalize → `git diff --exit-code` on `messages.pot`. A new/changed rider-facing string without a re-extract fails. |
| **G7** | Every PO compiles cleanly | `msgfmt --check --check-format --check-domain` on each `messages.po` |
| **G6** | Supported-language key-parity | `tools/check_catalog_parity.py`: the `en`, `es`, and `tl` catalogs have the template's exact msgid set |
| **G5** | Completeness + placeholder parity | same script: every `msgstr` non-empty; `{...}` field set identical source↔target (a dropped `{statewide}`/`{where}` would raise at `.format` time in a live refusal — exactly what this blocks) |
| **G3** | BCP 47 / RFC 5646 tag validity | `tools/check_bcp47.py`: `babel.Locale.parse` on every authored locale tag |

`msgfmt` is a system **gettext** binary (like `gitleaks`, not a uv/pip
dependency); CI installs it with `apt-get install -y gettext`. `pybabel` /
`babel.Locale` come from the `babel>=2.16` dev dependency (pure Python — no PyICU
/ native ICU build).

### The POT normalizer

`pybabel extract` emits volatile tokens (creation timestamp, Babel version, the
current year in the boilerplate comment) and a false-positive `python-format`
flag on any string containing a literal `%`.
[`tools/i18n_normalize_pot.py`](../tools/i18n_normalize_pot.py) freezes those
tokens and drops the spurious flag so the G2-lite diff is meaningful, not flaky.
The gate runs the normalizer on both authoring and CI, keeping the committed POT
byte-stable.

## Compiled `.mo` files are committed

The compiled `messages.mo` catalogs **are committed** (not gitignored).
Rationale: CI runs offline unit tests that assert the **Spanish and Tagalog** refusal text
(`tests/test_guards.py::test_spanish_pii_message_is_spanish`,
`test_spanish_injection_refused`) and the i18n seam tests, all of which load the
`.mo` at runtime via `gettext`. Committing `.mo` keeps every job green with local
== CI and no per-job compile step, and ships the translations in the wheel.
`.po` ↔ `.mo` drift is caught by those language-asserting tests; regenerate the
`.mo` after editing a `.po` with **`make i18n-compile`**.

## Workflow: adding or changing a rider-facing string

1. Wrap the English text in `_("…")` inside a helper in
   [`i18n.py`](../src/assistant/i18n.py) (use `.format()` for placeholders).
2. `make i18n` — re-extracts `messages.pot`; the G2-lite diff shows the new msgid.
3. Merge the new msgid into the catalogs: `uv run pybabel update -i
   src/assistant/locales/messages.pot -d src/assistant/locales
   --no-fuzzy-matching`, then fill the English `msgstr` (= msgid), Spanish, and Tagalog.
4. `make i18n-compile` to rebuild the `.mo`, then `make verify`.
5. Commit the changed `.py`, `messages.pot`, all three `messages.po` files, and
   all three `messages.mo` files.

## Corpus-content parity ceiling (documented 2026-07-09)

Language parity is bounded not only by this repo's code but by what the
agencies actually publish. Verified 2026-07-09 via the repo's polite fetch
pipeline (evidence in `docs/audits/eval-regression-2026-06-30.md`, addendum;
exclusion note in `corpus/manifest.yaml`):

- **MST publishes no genuinely Spanish Cal-ITP Benefits page.** The
  `/es/fares/benefits/` URL returns an untranslated shell — `<html lang="es">`
  around an article body byte-identical to the English page — unlike
  `/es/fares/`, which is really rendered in Spanish. Consequence: a Spanish
  question about MST reduced-fare self-verification cannot cite a Spanish
  source for the online path the English answer cites (`mst-fares-benefits`),
  which is the root cause of eval case `ml-012`'s EN/ES quality gap. This is
  a **corpus-content ceiling, not a code gap**: the honest exits are MST
  publishing a real translation (re-check periodically) or a maintainer
  adjusting `ml-012`'s expectation with a written rationale — never ingesting
  the English shell as `language: es`, and never a fabricated translation.

## Scope not yet covered (honest boundaries — Phase 3 follow-ons)

This Phase-1 pilot delivers the catalog + the PO-specific gates (G2/G3/G5/G6/G7)
for the fixed rider-facing strings. The following remain **future work**, tracked
as Phase 3 in [`I18N-MIGRATION-PLAN.md`](https://github.com/ChelseaKR/portfolio-standards/blob/main/I18N-MIGRATION-PLAN.md):

- **G11 `Vary: Accept-Language` negotiation** on the web handler / Lambda. Today
  the rider's language is inferred from question content (`detect_language`) and
  the handler does not negotiate on the HTTP `Accept-Language` header or set
  `Vary`/`Content-Language`. `i18n.negotiate_lang()` is implemented and tested so
  this is a wiring task, not new logic.
- **§7 disaggregated eval** — proving Spanish answer-quality holds within 5 points
  of English on a **native-ES** (not machine-translated) CA-civic benchmark. The
  multilingual eval suite exists, and as of 2026-07-17 a blocking parity gate
  (roadmap M-1, `evals/runner.py::check_parity` plus the committed-report check
  in `evals/check_report_regression.py`) fails any run or committed `EVALS.md`
  whose Spanish-vs-mirrored-English delta exceeds 5 points on 2+ cases. That
  gate measures parity against this repo's own mirrored cases; the **native-ES
  benchmark** half of §7 — an externally sourced, not machine-translated
  question set — remains outstanding equity work (needs a benchmark owner per
  the migration plan's open decisions).
- Other standard gates not implemented here: G1 (UTF-8 byte gate), G4
  (`html-has-lang` on `web/`, currently in the a11y suite), G9/G10
  (pseudolocale/RTL — frontend only; the assistant ships no RTL locale), and G12
  (CLDR/tzdata freshness pin — CLDR data is whatever the pinned `babel` bundles).
